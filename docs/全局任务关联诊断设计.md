# 全局任务关联诊断设计

## 1. 背景

当前系统已经具备基于单个任务号进行诊断的能力，能够围绕一个任务查询主任务详情、子任务、执行单、日志，并结合规则与大模型输出诊断结论。

但现有能力的分析粒度仍然是“单任务视角”，更适合回答：

- 当前任务为什么卡住
- 当前任务在哪个阶段异常
- 当前任务的日志中是否出现明显报错

对于仓储/WCS 场景中更常见的全局性问题，现有方案支持不足，例如：

- 当前任务是否被上游任务阻塞
- 某个设备、点位、容器是否形成系统瓶颈
- 当前任务只是受害者，还是整条阻塞链的根因任务
- 一个异常是否已经传播并影响多个任务

因此需要在现有单任务诊断能力之上，补充“全局任务关联诊断”能力。

---

## 2. 设计目标

### 2.1 目标

新增一种 global 模式，使系统在输入单个任务号后，不仅分析任务本身，还能自动扩展到与其相关的一组任务和资源，并输出阻塞链路分析结果。

系统需要能够回答以下问题：

1. 当前任务是否存在直接阻塞者
2. 当前任务所在链路的根阻塞源是谁
3. 当前链路的瓶颈资源是什么
4. 当前阻塞影响了哪些其他任务
5. 应优先处理哪个任务/资源

### 2.2 非目标

本阶段不追求：

- 构建全量实时任务图数据库
- 对全系统所有任务做秒级实时根因推断
- 完整替代现有单任务诊断逻辑
- 一次性覆盖所有业务场景与设备类型

本阶段目标是先交付一个可运行、可验证业务价值的 MVP。

---

## 3. 总体方案

采用“两层诊断体系”：

### 3.1 单任务诊断层

保留现有模式，用于分析单任务内部问题：

- 主任务详情
- 子任务状态
- 执行单状态
- 日志异常
- 规则命中
- LLM 总结

### 3.2 全局关联诊断层

在 global 模式下，引入以下流程：

1. 查询目标任务详情
2. 提取关联键
3. 查询时间窗内候选关联任务
4. 识别关联关系
5. 推断直接阻塞者与根阻塞源
6. 识别瓶颈资源
7. 生成结构化分析结果
8. 输出总结与处置建议

---

## 4. 核心概念

### 4.1 分析对象

- **focusTask**：用户输入的当前任务
- **relatedTasks**：与当前任务强相关的一圈候选任务
- **directBlocker**：直接阻塞当前任务的候选任务
- **rootBlocker**：整条链上最早导致阻塞传播的候选任务
- **bottleneckResource**：当前链路中的关键瓶颈资源

### 4.2 关联关系

MVP 阶段优先支持以下关系：

1. **同容器**
   - `containerCode` 相同
   - 用于识别容器未释放、同容器链路阻塞

2. **同设备**
   - 子任务或执行单的 `deviceCode` 相同
   - 用于识别设备繁忙、设备故障、执行排队

3. **同点位**
   - `businessFrom` / `definiteFrom` / `businessTo` / `definiteTo`
   - 或执行单 `startPoint` / `endPoint`
   - 用于识别起点/终点占用、路径冲突

4. **同时间窗**
   - 与目标任务在同一时间窗内出现的候选任务
   - 用于辅助判断“谁先卡住、谁后受影响”

## 5. 诊断流程设计

### 5.1 输入

请求体新增字段：

- `taskId`：任务 ID 或 WMS 任务号
- `scope`：`single` 或 `global`
- `timeWindowMinutes`：全局分析时间窗，默认 30 分钟

### 5.2 流程

#### Step 1：查询目标任务

根据 `taskId` 查询主任务、子任务、执行单等信息，形成分析中心任务。

#### Step 2：提取关联键

从目标任务中提取候选关联键：

- `containerCode`
- `businessFrom`
- `definiteFrom`
- `businessTo`
- `definiteTo`
- `taskItems[].deviceCode`
- `tickets[].deviceCode`
- `tickets[].startPoint / endPoint`

#### Step 3：查询候选关联任务

在目标任务时间窗内，按关联键查询候选任务集合。

#### Step 4：构建局部关系快照

为每个候选任务标记：

- 关联类型
- 关联原因
- 时间先后关系
- 是否已完成
- 是否有报错

并生成关系边：

- `same_container`
- `same_device`
- `same_source_point`
- `same_target_point`
- `upstream_blocked`

#### Step 5：识别直接阻塞者

优先选择满足以下条件的候选任务：

- 与当前任务存在强关联
- 创建时间早于或等于当前任务
- 尚未完成
- 可能仍占用当前任务所需资源

#### Step 6：识别根阻塞源

优先从候选任务中选择：

- 创建时间更早
- 自身存在明确异常或失败状态
- 对更多下游任务有影响

#### Step 7：识别瓶颈资源

统计候选任务在容器、设备、点位上的聚集情况，识别可能的瓶颈资源。

#### Step 8：输出结构化结果

输出：

- 当前任务
- 直接阻塞候选
- 根阻塞候选
- 影响任务列表
- 关系边
- 瓶颈资源
- 根因说明
- 建议动作

## 6. 数据模型设计

### 6.1 请求模型

`DiagnoseRequest` 新增：

- `scope`
- `timeWindowMinutes`

### 6.2 响应模型

`DiagnoseResponse` 新增：

- `analysisScope`
- `relationSnapshot`

其中 `relationSnapshot` 包括：

- `focusTaskId`
- `directBlockerTaskId`
- `rootBlockerTaskId`
- `impactedTaskIds`
- `relatedTasks`
- `dependencyEdges`
- `bottleneckResources`

### 6.3 关系边模型

`TaskRelationEdge`

字段建议：

- `fromTaskId`
- `toTaskId`
- `relationType`
- `resourceKey`
- `description`

### 6.4 瓶颈资源模型

`ResourceBottleneck`

字段建议：

- `resourceType`
- `resourceKey`
- `description`
- `impactedTaskCount`

## 7. 服务拆分设计

### 7.1 DiagnosisFacade

职责：

- 保持统一入口
- 根据 `scope` 分发到单任务模式或全局模式

### 7.2 DiagnosisContextAssembler

职责：

- 继续为单任务模式组装上下文

### 7.3 GlobalDiagnosisContextAssembler

职责：

- 查询目标任务
- 计算时间窗
- 查询候选关联任务
- 构建关系快照
- 收集证据

### 7.4 GlobalDiagnosisService

职责：

- 编排全局分析流程
- 输出结构化诊断结果
- 生成 summary、rootCauses、actions

### 7.5 TaskClient

新增能力：

- `findRelatedTasks(TaskDetail focusTask, LocalDateTime windowStart, LocalDateTime windowEnd, String env)`

用于支持基于多种关联键的候选任务查询。

## 8. 数据访问设计

### 8.1 当前能力

当前 `TaskClient` 已支持按 `taskId` 查询单个任务。

### 8.2 新增能力

需要支持在时间窗内按以下条件查询候选任务：

- 同容器
- 同点位
- 同设备
- 同任务号/同业务号

### 8.3 JDBC 实现建议

全局关联分析只查询当前运行中的业务表，不查询历史表。原因是历史表中的任务均已完成，不参与当前阻塞链、资源占用与排队关系的判断。

MVP 阶段优先基于以下当前表构建候选任务集合：

- `tas_task`
- `tas_task_item`
- `acs_ticket`

查询策略：

1. 先从 `tas_task` 中按时间窗、容器、点位、任务号等条件筛出主任务候选集
2. 再结合 `tas_task_item` 的设备维度补充同设备关联
3. 必要时结合 `acs_ticket` 的设备与起终点信息补充更细粒度关系

注意事项：

- 不回查 `his_tas_task`
- 不回查 `his_tas_task_item`
- 不回查 `his_acs_ticket`
- 若目标任务在当前表不存在，则按“当前无活动任务”处理，而不是切换到历史链路分析

MVP 阶段可先使用多条件 SQL 聚合候选任务，后续再进一步优化查询性能。

## 9. 规则与推断策略

### 9.1 MVP 阶段采用启发式规则

直接阻塞者候选识别：

- 与目标任务强关联
- 更早出现
- 尚未完成

根阻塞候选识别：

- 未完成或失败
- 有错误信息
- 时间更早

瓶颈资源识别：

- 同资源聚集的候选任务数量较多

### 9.2 后续增强方向

后续建议引入明确阻塞类型：

- `SELF_ERROR`
- `UPSTREAM_BLOCKED`
- `RESOURCE_BUSY`
- `POINT_OCCUPIED`
- `CONTAINER_LOCKED`
- `SCHEDULING_BACKLOG`

并把全局规则从上下文组装器中拆出，沉淀到独立分析器中。

---

## 10. 与 LLM 的协作方式

本阶段建议：

- 全局模式优先由程序进行结构化推断
- LLM 负责总结、解释与建议补充
- 不建议直接让 LLM 从原始日志中自主推断复杂的全局阻塞链

原因：

1. 全局链路分析需要稳定、可解释
2. 结构化证据更适合前端展示
3. LLM 适合增强表达，但不应作为唯一根因引擎

## 13. 风险与注意事项

1. **候选任务过多**
   - 时间窗过大、关联条件过宽时，可能导致噪声过多
   - 需要在查询和排序策略上控制规模

2. **不同环境接口能力不一致**
   - JDBC 可以较容易实现关联查询
   - HTTP 模式下如果后端缺少聚合接口，能力会受限

3. **任务字段语义不完全统一**
   - `taskId`、`wmsTaskNo`、子任务 ID、执行单 ID 需要明确边界

4. **启发式推断存在误判可能**
   - MVP 阶段只能作为候选分析，不能承诺 100% 精准
   - 前端与文案中应体现“候选”语义

## 15. 结论

本方案的核心思路不是推翻现有单任务诊断，而是在其基础上新增一层“局部全局视角”分析能力。

这样可以以较低成本实现：

- 从单任务定位升级到链路定位
- 从点状诊断升级到关联诊断
- 从“当前任务为何卡住”升级到“谁导致了一串任务卡住”

该方案适合作为当前项目的下一阶段演进方向。该阶段完成后，再决定是否继续向更复杂的图模型或实时全局分析架构演进。
